# esp-ax25

esp-ax25 is a pure C AX.25 protocol stack for ESP-IDF. It is aimed at ESP32-class systems that need packet radio features such as connected-mode AX.25 sessions, UI frames, routing between multiple interfaces, KISS interoperability, and TCP-accessible monitoring or server endpoints.

The project is structured as an ESP-IDF component with reusable library code, example applications, and a dedicated test suite. It is designed for embedded use: configuration is runtime-accessible, modules are thread-safe at the public API level, and the router decouples protocol handling from the underlying transport.

Note this library is mostly generated by AI and curated/architected by a developer.  The idea was to create a library were AI can use the examples to know how to generate apps using esp-ax25.  

## Features

- Pure C implementation for ESP-IDF projects
- AX.25 frame and address encoding/decoding
- Connected-mode AX.25 sessions with timers, retries, and callbacks
- UI frame support for beacons, monitoring, and application traffic
- Router-based port model with static, default, promiscuous, digipeater, and dynamic ports
- KISS framing support for TNC interoperability
- AGWPE protocol support for both TCP client and server integrations
- UART, TCP, WiFi, and Bluetooth-oriented transport building blocks
- Periodic beacon transmission module
- Digipeater module built on router next-hop matching
- Runtime configuration system backed by a central schema and NVS-aware application setup
- Logging, frame printing, TCP log streaming, and monitor server support
- Unit tests and stress-test applications alongside example firmware

## Main Components

### Core Protocol Types and Codecs

The address, frame, and type modules define the protocol building blocks used throughout the project. These files handle AX.25 addresses, frame formats, payload fields, and related utility types.

- `ax25_address`: callsign and SSID parsing/formatting
- `ax25_frame`: AX.25 frame construction and decoding
- `ax25_types`: shared constants, enums, callbacks, and protocol-level types
- `ax25_print`: human-readable frame/debug output helpers

### Configuration

`ax25_config` provides a central runtime configuration layer. Example applications initialize it early with `ax25_cfg_init()` and typically seed transport- or app-specific values by calling `ax25_cfg_set()` from Kconfig-derived settings. This keeps the library logic independent from compile-time-only configuration.

### Router

`ax25_router` is the central dispatch layer. Applications call `ax25_router_init()` once, register one or more ports, and then route decoded frames with `ax25_router_send()`.

The router supports five delivery modes:

- `AX25_PORT_STATIC`: deliver frames to a specific destination
- `AX25_PORT_DEFAULT`: destination when no specific port matches
- `AX25_PORT_PROMISCUOUS`: receives all traffic
- `AX25_PORT_DIGIPEATER`: matches the next unrepeated digipeater hop
- `AX25_PORT_DYNAMIC`: bind to the first source address sent, then behave like a static port

This port model is what lets the project bridge UART TNCs, TCP clients, monitoring tools, digipeater logic, and application handlers without forcing all logic into a single task.

Delivery is asynchronous and buffered per port. `ax25_router_send()` decides which ports should receive a frame, enqueues a copy for each matching port, and returns without waiting for every destination callback to finish. This keeps a slow monitor client or application handler from stalling unrelated paths, at the cost of finite per-port queue depth: if a port falls behind badly enough, frames for that port can be dropped while other ports continue to run.

### Connected Mode

`ax25_conn` implements a single AX.25 connected-mode session with state management, timers, retry handling, and application callbacks. It is the module used by interactive and scripted connection examples. Applications provide callbacks for received data, outgoing frames, connect/disconnect events, and optional error or link-reset handling.

### Beaconing

`ax25_beacon` provides periodic UI-frame transmission. Once initialized after the router is available, an internal timer wakes a worker task that builds and routes configured beacon frames through normal router delivery rules, which means the same PHY and routing setup used for other traffic can also carry beacons.

### Digipeating

`ax25_digipeater` registers a digipeater-mode router port when a digipeater callsign is configured. The router handles next-hop matching and H-bit updates; the module queues matched relay frames to an internal worker task, which then invokes the application-provided transmit callback.

### PHY and Transport Integration

The project keeps physical I/O separate from protocol logic. The component includes transport-oriented modules for common integration patterns:

- `ax25_phy_kiss_uart`: KISS-over-UART integration with a hardware TNC
- `ax25_phy_kiss_tcp_client`: connect to a remote KISS server such as a PC running Soundmodem
- `ax25_phy_kiss_bt`: Bluetooth SPP transport for KISS traffic
- `ax25_phy_tcp_server`: TCP server building block used by higher-level servers
- `ax25_wifi` and `ax25_uart`: transport support helpers for ESP-IDF apps

The TCP-oriented transport modules use bounded asynchronous TX queues, and UART KISS frame transmission is also queued to a dedicated worker task. A successful send call means the payload was accepted for transport and queued, not that the bytes have already reached the remote peer or TNC. This prevents application tasks, router callbacks, or protocol handlers from blocking on socket or UART backpressure, but it also means callers need to treat queue depth as a real runtime limit. If a transport queue is full, the send API returns `ESP_ERR_NO_MEM` and the caller must decide whether to retry, drop, or back off.

### External Protocol Servers

The component also includes higher-level server modules that expose AX.25 traffic to external tools:

- `ax25_kiss_tcp_server`: share router traffic with KISS TCP clients
- `ax25_agwpe`: AGWPE protocol encode/decode helpers shared by both client and server paths
- `ax25_agwpe_server`: expose local AX.25 traffic to AGWPE-compatible TCP clients
- `ax25_agwpe_client`: connect to a remote AGWPE server, decode inbound AGWPE frames, and queue outbound AGWPE requests or traffic
- `ax25_monitor_tcp_server`: TCP-accessible monitoring path for AX.25 traffic
- `ax25_log` and `ax25_log_tcp_server`: export ESP-IDF log output over TCP

### KISS client and server support

The component supports both sides of networked KISS integration.

`ax25_phy_kiss_tcp_client` lets an ESP-IDF application connect to a remote KISS server such as Soundmodem or another TNC-over-TCP endpoint. It owns the socket lifecycle, decodes inbound KISS frames through the configured callback, and queues outbound AX.25 frames to a dedicated TX worker so router or application code does not block on socket backpressure.

`ax25_kiss_tcp_server` exposes local router traffic to one or more KISS TCP clients. This is the path used by the KISS-serving examples when the ESP device should act as the TCP endpoint for external host software.

Together, these modules cover the common KISS deployment patterns:

- ESP as a KISS TCP client of an existing software TNC or modem host
- ESP as a KISS TCP server for external packet-radio tools
- Mixed routing topologies where router traffic is bridged between UART KISS, TCP KISS, Bluetooth KISS, and local application handlers

### AGWPE client and server support

The component supports both AGWPE roles.

`ax25_agwpe_server` exposes local AX.25 traffic to AGWPE-compatible TCP clients and is the AGWPE-serving path used by `examples/agwpe_server` and `examples/agwpe_kiss_server`.

`ax25_agwpe_client` supports the inverse role: connecting an ESP-IDF application to a remote AGWPE server when the ESP device should act as an AGWPE-speaking host rather than serving AGWPE clients itself.

The public AGWPE client API covers common operations including:

- Version, port-info, port-capability, and heard-list requests
- Callsign registration and unregistration
- Monitor and raw-stream enable requests
- Raw AX.25 frame transmission
- Unproto transmission with or without digipeaters
- Connected-mode connect, disconnect, outstanding-frame queries, and data send helpers

The AGWPE server path is router-facing: it accepts TCP clients, translates AGWPE commands into local AX.25 actions, and can surface local traffic back to connected AGWPE software. The AGWPE client path is narrower in scope: it manages the TCP socket, reconnect behavior, inbound AGWPE decoding, and outbound frame queueing, then delivers decoded AGWPE frames through an application callback.

Unlike the server examples above, the AGWPE client path is currently exposed as a reusable library module rather than a dedicated example application. The application is expected to provide the AGWPE frame callback and decide whether decoded remote traffic is logged directly, converted into local AX.25 frames, or bridged into router or `ax25_conn` logic. It does not automatically register router ports or create local `ax25_conn` sessions from remote AGWPE events.

## API and Callback Flow

Most components in esp-ax25 follow the same integration pattern: they receive input through normal API calls and deliver output through callbacks supplied by the application.

In practice, that means the application owns the outer event loop, transport, and policy decisions:

- A PHY module receives bytes from UART, TCP, or Bluetooth and reports decoded frames through an `on_frame` callback.
- The application or PHY callback passes those frames into the router with `ax25_router_send()`.
- The router delivers frames to registered ports by invoking each port's `on_frame` callback.
- Higher-level modules such as `ax25_conn` accept incoming frames through API calls such as `ax25_conn_on_frame()` and emit outgoing frames, received payloads, and state changes through callbacks.
- Optional modules such as the digipeater and beacon modules also rely on this pattern: the application initializes them through APIs, and actual transmission happens through router delivery or worker-task-mediated application callbacks.

This design keeps the protocol modules transport-agnostic. The stack does not require a single built-in I/O path; instead, applications connect modules together by wiring callbacks between the router, PHY layers, connection handlers, and external server interfaces.

One consequence of the asynchronous router and transport paths is that callback completion and physical I/O completion are intentionally decoupled. `ax25_router_send()` returning `ESP_OK` means the frame was accepted for per-port delivery. Likewise, TCP KISS client, TCP server, UART KISS, and digipeater relay helpers returning `ESP_OK` mean the outgoing work was queued for transport or relay processing. If an application needs stronger delivery semantics, it must add its own acknowledgement or retry policy above the transport layer.

## Architecture Summary

For the main outbound paths, it is useful to think in terms of three layers:

- Router delivery: `ax25_router_send()` matches destination ports, enqueues frame copies to the selected port queues, and returns once delivery has been accepted for those ports.
- Module workers: modules such as `ax25_conn`, `ax25_beacon`, `ax25_digipeater`, `ax25_kiss_tcp_server`, `ax25_monitor_tcp_server`, and `ax25_agwpe_server` may do additional formatting, state handling, or relay work in their own task or worker context rather than directly in the caller's callback.
- Physical transport: TCP KISS client, AGWPE client, TCP server connections, and UART KISS use dedicated TX workers so socket or UART backpressure does not block higher-level callbacks. The AGWPE client also runs a dedicated RX task to decode the remote byte stream into protocol frames.

In practice, that means `ESP_OK` usually means accepted or queued, not physically delivered. If a queue is full, the relevant send path returns `ESP_ERR_NO_MEM` or drops work locally, depending on that module's contract. The AGWPE client follows the same rule: a successful request or send call means the encoded AGWPE frame was queued for socket transmission. If your application needs proof of remote receipt, it must implement that above these transport and relay layers.

## Getting Started

### Requirements

- ESP-IDF 5.x or newer
- One of the supported ESP32-family targets listed in `idf_component.yml`
- A transport path appropriate for your use case, such as a UART-attached KISS TNC or a reachable KISS-over-TCP endpoint

### Build an Example

Build from an example application directory, not from the component root. For example:

```bash
cd examples/ui_beacon
idf.py menuconfig
idf.py build
idf.py flash monitor
```

Other examples follow the same pattern from their own directories under `examples/`.

### Quick Integration Flow

The examples consistently follow this startup sequence:

1. Initialize NVS when the selected ESP-IDF services require it.
1. Call `ax25_cfg_init()`.
1. Seed runtime configuration values with `ax25_cfg_set()` as needed.
1. Call `ax25_router_init()`.
1. Initialize the chosen PHY, client, or server module.
1. Register router ports that connect the PHY, application logic, or services.
1. Add optional modules such as `ax25_conn`, `ax25_beacon`, or `ax25_digipeater`.

The simplest place to start is `examples/ui_beacon`, which shows a minimal router plus UART KISS transport setup. For connected-mode work, `examples/connected_chat` is the best next step.

## Examples

Each example is a standalone ESP-IDF application that demonstrates a different integration pattern.

### ui_beacon

`examples/ui_beacon` is the smallest end-to-end example. It initializes the router, attaches a UART KISS PHY as the default output path, registers an application port, and periodically sends UI beacon frames. Start here if you want the shortest path to transmitting AX.25 traffic from an ESP32.

### connected_chat

`examples/connected_chat` demonstrates interactive connected-mode AX.25 communication with `ax25_conn`. It wires a local application port to the connection handler, forwards outbound frames through a UART KISS PHY, and exposes a small command interface for connect, send, disconnect, and status operations.

### monitor

`examples/monitor` connects to a remote KISS-over-TCP soundmodem over WiFi, forwards received traffic into the router, and prints decoded AX.25 frames. It is an example of connecting to
a networked KISS server as the default router port.

### kiss_router

`examples/kiss_router` shows the router as a bridge between interfaces. The default path is a UART KISS TNC, and the example can also expose a KISS TCP server over WiFi and a Bluetooth SPP interface depending on configuration. This is the clearest example of the project's multi-port routing model.

### agwpe_server

`examples/agwpe_server` exposes AX.25 traffic to AGWPE-compatible TCP clients while using a UART KISS TNC as the default radio-side transport. Use this as the reference for AGWPE integration with a single router instance and multiple network clients.

### agwpe_kiss_server

`examples/agwpe_kiss_server` combines both external protocols in one application: AGWPE for compatible client software and KISS TCP for KISS-aware tools. It is useful when one device needs to serve multiple kinds of host software at the same time.

### client

`examples/client` is a scripted connected-mode client. It uses `ax25_conn` over UART KISS, waits for expected prompts from a remote station, sends predefined commands, and disconnects cleanly. It is a useful reference for automating BBS-style interactions rather than building an interactive console.

## Tests and Validation Targets

- `test/` contains the unit-test the component test cases.
- `test_stress/` contains a stress-oriented test for ax25_router.

Build these the same way as the examples by changing into the target directory and running `idf.py build`.
